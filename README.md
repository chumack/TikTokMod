# TikTokMod

Кроссплатформенное десктоп-приложение для Windows и Linux: встроенный браузер
TikTok, скачивание видео (приоритет форматов без watermark), массовая загрузка
по ссылке на профиль автора и настройки маршрутизации трафика для обхода
региональных ограничений.

## Установка

Текущая версия — **0.3.3**. Один релиз на GitHub содержит и Windows, и Linux.

### Windows

Установщик для Windows: `TikTokMod-Setup-0.3.3-x64.exe`.

- Установка **для всех пользователей** — установщик запрашивает права
  администратора. Папка по умолчанию — `C:\Program Files\TikTokMod`; на странице
  установки её можно заменить на любую другую.
- **Никаких чужих учётных данных в сборке нет.** Настройки, cookies и сессия
  встроенного браузера хранятся в профиле пользователя (`%APPDATA%\tiktok-mod`
  на Windows) и создаются с нуля при первом запуске. Входите в свой аккаунт
  TikTok сами — через вкладку «Обзор» или раздел «Настройки».
- Удаление программы удаляет и профиль: cookies, настройки и кэш исчезают, при
  следующей установке приложение снова открывается чистым. Чтобы сохранить
  профиль, удалите папку `C:\Program Files\TikTokMod` вручную, не запуская
  деинсталлятор.

Для тех, кому установка не нужна, есть portable-сборка
`TikTokMod-Portable-0.3.3-x64.exe` — запускается напрямую, ничего не регистрируя
в системе.

> Версия 0.1.0 ставилась только для текущего пользователя, а 0.2.x — для всех.
> Это разные записи в реестре, поэтому перед установкой 0.2.x удалите 0.1.0
> через «Параметры → Приложения», иначе обе копии останутся на машине.

### Linux

Три файла, и в каждом `yt-dlp` с `ffmpeg` лежат внутри — отдельно их ставить не
нужно:

| Файл                         | Что это                              | Как ставить                     |
| ---------------------------- | ------------------------------------ | ------------------------------- |
| `TikTokMod-0.3.3.AppImage`   | Один файл, ничего не пишет в систему | `chmod +x` и запуск             |
| `tiktok-mod_0.3.3_amd64.deb` | Обычный пакет: меню, иконка, `apt`   | `sudo apt install ./файл.deb`   |
| `tiktok-mod-0.3.3.tar.gz`    | Просто распакованная папка           | распаковать, запустить бинарник |

**Manjaro и прочие дистрибутивы на Arch** — правильный путь AppImage: пакетным
менеджером там pacman, а не dpkg, так что `.deb` не ставится штатно.

```bash
chmod +x TikTokMod-0.3.3.AppImage
./TikTokMod-0.3.3.AppImage
```

Настройки, cookies и сессия встроенного браузера лежат в `~/.config/tiktok-mod`
и создаются с нуля при первом запуске.

AppImage запускается через FUSE, поэтому нужен пакет `fuse2`
(`sudo pacman -S fuse2`). Ставить его не хочется — AppImage распакует себя сам:

```bash
./TikTokMod-0.3.3.AppImage --appimage-extract-and-run
```

`.deb` предназначен для Debian/Ubuntu и производных. Зависимости стандартные —
`gtk3`, `nss`, `alsa-lib`, `libxss1`; на Manjaro и Ubuntu они обычно уже есть.

## Запись эфиров

Кнопка **«Запись трансляции»** стоит в нижней панели вкладки **«Обзор»**, рядом
с «Скачать текущее видео». Отдельной вкладки нет: записывать имеет смысл ровно
то, что показывает встроенный браузер, поэтому и кнопка живёт там же.

Ссылку вводить не нужно — источник берётся со страницы, которая сейчас открыта
во встроенном браузере. Нажмите кнопку, и приложение:

- если вы на странице трансляции (`…/@ник/live`) — сразу определит эфир и начнёт
  запись;
- если вы в ленте или на профиле — покажет компактный список найденных на
  странице эфиров, чтобы выбрать один кликом. Автовыбор первого видимого не
  делается осознанно: в ленте постоянно мелькают чужие превью трансляций, а
  «записал не то» хуже одного лишнего клика;
- если эфиров на странице нет — подскажет, что надо открыть трансляцию.

Панель свёрнута в одну строку кнопок и разворачивается сама, когда есть что
показать (ошибка, карточка эфира, выбор) или когда идёт запись. В развёрнутом
виде там же выбирается режим и галочка «с чатом», и живёт список идущих записей
с кнопками «Остановить», «Остановить всё» и «Очистить».

Файлы пишутся в `<папка загрузок>\live\` сразу в формате `.mp4`. Есть два
режима.

### Режим «Поток» (по умолчанию)

Берёт прямой URL из `webcast/room/info` — тот же путь, который используют все
открытые рекордеры TikTok — и пишет через `ffmpeg -c copy`.

- **Запись стартует с лучшего доступного качества.** Нельзя выбрать конкретное
  (720p/1080p) — TikTok сам отдаёт один набор потоков на эфир.
- Без перекодирования: качество не меняется, нагрузка на процессор нулевая,
  расход места равен битрейту потока.
- Файл **фрагментированный** (`frag_keyframe+empty_moov`): его можно открыть и
  досмотреть, даже если приложение выключили или запись упала. Обратная сторона
  — `+faststart` не используется, поэтому в некоторых проигрывателях начало
  файла «подгружается» чуть дольше. Это осознанный размен: целостность важнее
  скорости старта.
- Остановка («Остановить» или «Остановить всё») сначала просит ffmpeg закрыть
  контейнер, поэтому запись остаётся цельной. Если поток молчит больше двух
  минут, запись останавливается сама и файл сохраняется.

### Режим «Экран (как на странице)»

Пишет ровно то, что видно во встроенном браузере: вертикальное видео, панель
зрителей и колонку чата. Приложение снимает кадры гостя
(`webContents.capturePage`) и кодирует их в H.264.

Звук идёт из потока TikTok, но **отдельным процессом**: он перекодируется в AAC
побочно, а в конце записи приклеивается к готовому видео. Отдельно — не из
эстетики. Проверено на живом эфире: когда CDN-поток подключается вторым входом
того же ffmpeg, он застревает на пробинге подписанного URL (неограниченная
работа ДО начала записи, флага «неблокирующий вход» не существует), ffmpeg
перестаёт читать кадры и файл остаётся на 36 байтах — 197 кадров захвачено, ноль
записано. Раздельные процессы означают, что упавший, запрещённый или
закончившийся аудиопоток не может уронить видеозапись: в худшем случае файл
получится без звука, и приложение так и напишет в строке записи.

Когда нужен именно этот режим:

- эфир идёт, а «Поток» не стартует или пишет чёрное;
- нужно сохранить **то, что видит зритель**, вместе со списком зрителей и чатом;
- качество на эфире низкое, а интерфейс страницы его повышает.

Честно о его цене:

- Это перекодирование: примерно треть ядра на 720p и 0.5–1.5 ГБ на час, против
  нуля у режима «Поток». Для многочасовых записей на ноутбуке это заметный
  нагрев.
- **Окно нельзя сворачивать**, а вкладку «Обзор» — уводить в фон. Скрытое окно
  Chromium перестаёт отрисовывать (electron#31992/#39029), кадры идут пустыми;
  через пять пустых кадров подряд запись останавливается сама с объяснением,
  чтобы не получить час чёрного файла.
- Записывается ровно та область страницы, ради которой всё и затевалось:
  **карточка плеера вместе с колонкой чата, то есть всё, что левее правого края
  окна и правее колонки навигации TikTok**. Граница берётся из реальных
  прямоугольников самой страницы: карточка плеера ищется подъёмом от играющего
  `<video>`, чат — по собственному заголовку «Зрители», колонка навигации
  («Назад», «Начать эфир», «Подписки»…) отрезается по своему правому краю. Это
  принципиально отличается от прежних попыток «угадать, где окно»: на широком
  окне меню занимает больше половины экрана, и трансляция выходила в кадре
  крошечной полосой с неверными пропорциями. Полноэкранный просмотр
  обрабатывается отдельно — TikTok прячет меню сам, и тогда пишется весь экран.
- Кадр **никогда не обрезается**. Если прямоугольник страницы меняет форму
  (открылся док записи, окно перетащили, сменился полный экран), картинка
  вписывается в зафиксированный размер целиком, с сохранением пропорций, а
  свободное место закрывается чёрными полосами. Раньше вместо этого кадр
  обрезался по центру, и пропадала то шапка плеера, то правый край чата. Цена
  решения честная: размер выходного кадра фиксируется в момент старта (поток
  сырых пикселей не умеет менять геометрию на ходу), поэтому страница должна
  дойти до окончательного вида до нажатия «Запись».
- Кадры берутся **из самой отрисовки страницы** (`beginFrameSubscription`), а не
  снимками экрана. Снимок — это копия поверхности со снятием в GPU и переходом в
  главный процесс, и на окне 2466×713 он занимает ~200 мс, то есть сам по себе
  ограничивает запись пятью кадрами в секунду, сколько бы кодер ни был бы
  быстрым. Когда браузер умеет отдавать кадры из компоновщика, верхняя граница
  становится частотой перерисовки страницы — обычно **5–15 кадров в секунду**;
  настоящая цифра показана прямо в строке записи («N кадр/с»). Длительность при
  этом **настоящая**: ffmpeg штампует кадры реальным временем
  (`-use_wallclock_as_timestamps`), а не фиксированной частотой. Без этого файл
  проигрывался бы втрое-вчетверо быстрее — ровно тот баг, который был. Если
  подписка недоступна, запись сама переходит на снимки экрана и продолжает
  работать — просто медленнее.
- **25 кадров в секунду на полное окно недостижимы в Electron.** Это ограничение
  платформы, а не настройка: `capturePage` идёт через GPU-readback, и для 25 fps
  нужен нативный захват (DWM/DXGI), которого у Electron нет. Если нужна такая
  частота — записывайте эфир в режиме «Поток»: там кадры не снимаются вообще, а
  пишутся напрямую из трансляции.
- Кадр уходит в ffmpeg **сырыми пикселями**, без сжатия (`rawvideo`/BGRA). PNG
  стоил по ~500 КБ на кадр, и ffmpeg успевал распаковывать лишь 3–5 штук в
  секунду — то есть bottleneck был в кодировщике, а не в захвате. Ограничение
  размера кадра (**не шире 1600 px и не больше ~0.9 Мпикс**) осталось, но теперь
  оно ограничивает объём данных в трубе, а не скорость распаковки.
- Геометрия файла **фиксируется по первому кадру** и больше не меняется. Высота
  окна во время записи скачет сама (3004×883 → 3004×793, когда страница
  перестроилась), и без этого в один mp4 попадали кадры разной высоты: плеер
  брал размер дорожки из первого кадра и растягивал остальные — это и выглядело
  как «сплющенная картинка». Теперь каждый кадр приводится ровно к размеру
  холста.
- **Чёрных полос нет.** Раньше кадр вписывался в холст фильтром
  `scale=…:decrease,pad=…`, и любая кадровая картинка, отличающаяся от холста по
  пропорциям на пару процентов, получала рамку. Теперь кадр растягивается ровно
  в холст: цена — искажение пропорций не более ~2 % и только в момент, когда
  страница сама перестроилась.
- **Звук берётся из того же браузера, что и картинка, поэтому идёт синхронно.**
  Пока звук тянулся отдельным процессом ffmpeg прямо с CDN, а картинка снималась
  с окна со встроенным браузером, рассинхрон был гарантирован: картинка отстаёт
  на столько, сколько Chromium уже буферизовал в плеере (2–5 с), и эта величина
  гуляет. Чинить её подбором нельзя — API, который сообщает задержку плеера, не
  существует: `video.buffered` для живого потока молчит,
  `getVideoPlaybackQuality()` отдаёт только счётчики. Проверено четыре попытки:
  сдвиг по времени первого аудиобайта давал рассинхрон ровно величиной сдвига
  (сначала 3.8–7 с, затем 2.4–6 с); сумма двух задержек — жёсткий рассинхрон.
  Теперь звук снимается **из гостя** через `setDisplayMediaRequestHandler`
  (`audio: guest.mainFrame`, `enableLocalEcho: true`) и пишется отдельным
  коротким процессом в `.guest.webm`, а при склейке компенсируется только
  измеренная разница между моментом старта видео и моментом старта звука —
  обычно **0.2 с** вместо прежних секунд. Оба сигнала берутся уже после задержки
  плеера, поэтому рассинхрон не накапливается и не требует подстройки. Если
  браузер не даст дорожку, запись спокойно продолжается без звука, а причина
  пишется в журнал `live\_screen.log` рядом с загрузками. Поле «сдвиг звука»
  убрано — настраивать нечего.
- Запись оставляет **один файл**. Промежуточный беззвучный `.video.mp4`
  удаляется, как только успешная склейка дала финальный файл со звуком.

Одновременно можно писать **не больше трёх** эфиров и **не больше одного** в
режиме «Экран». Закрытие приложения корректно завершает записи — они не
теряются.

### Как пользоваться

1. Откройте трансляцию во встроенном браузере на вкладке «Обзор» — просто
   кликните по эфиру в ленте, как обычно. Если лента не прогрузилась, кнопка
   **«Обновить»** на верхней панели перезагружает страницу на месте —
   перезапускать приложение не нужно.
2. Выберите режим в нижней панели: **«Поток»** или **«Экран»**. Галочки «чат» и
   «звук» относятся к режиму «Экран» — при «Потоке» они гаснут и не нажимаются,
   потому что там звук идёт вместе с видео из одного источника, а чат снимать не
   с чего. При переходе на «Экран» обе включаются сами.
3. Нажмите **«Запись трансляции»**. Приложение определит эфир и начнёт писать.
   Панель занимает одну строку и не меняет высоту, так что вёрстка встроенного
   браузера не прыгает и кадр не расходится с размером холста.
4. Кнопка **«Очистить»** в той же панели снимает чипы записанных трансляций.
   Файлы на диске она не трогает: пропадает только строка с кнопками «Показать».
   Пока идёт хотя бы одна запись, кнопка неактивна.

Ограничения:

- Режим «Поток» позволяет переключаться на другие вкладки и работать дальше.
  Режим «Экран» — нет: вкладку «Обзор» нельзя уводить в фон, а окно —
  сворачивать.
- Приватные эфиры («только для подписчиков») и эфиры с возрастным ограничением
  требуют, чтобы в **«Обзоре»** был выполнен вход в аккаунт — приложение
  использует сессию встроенного браузера. Без входа доступны только открытые
  эфиры.
- Эфиры могут быть недоступны из вашего региона. Приложение сообщит об этом
  отдельной подсказкой; помогает прокси из раздела «Настройки».
- Формат потоков и названия пунктов меняются на стороне TikTok. Если эфир идёт,
  а запись не начинается, — это почти всегда смена формата на их стороне.
- Если эфир не отдаёт аудиопоток, видео в режиме «Экран» всё равно запишется —
  просто без дорожки, и строка записи честно напишет «без звука». Галочка «со
  звуком» управляет только тем, пытается ли приложение вообще его тянуть.

### Чат эфира

Галочка **«с чатом»** включена по умолчанию и находится в той же нижней панели.
Рядом с видео появляются два файла с тем же именем:

| Файл               | Что внутри                                                                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<имя>.chat.jsonl` | Одна JSON-строка на сообщение: `t` (ISO 8601), `ts` (мс), `msgId`, `displayId`, `nickname`, `content`. Удобно для анализа и для импорта в софт с поддержкой TikTok.                                 |
| `<имя>.chat.srt`   | Субтитры. Реплики идут подряд, пока их не прервёт следующая — как в обычных субтитрах к записи интервью. Временная шкала отсчитывается от начала записи, так что `.chat.srt` ложится поверх `.mp4`. |

**Главное условие: «Обзор» должен быть открыт на этом эфире.** Кнопка записи как
раз в «Обзоре», так что условие выполняется автоматически — просто не уходите на
другую страницу, пока идёт запись с чатом.

Сейчас чат берётся **из DOM-колонки на странице**: приложение наблюдает за
блоком сообщений и вычитывает всё, что в нём появляется. Это работает, но у
такого способа есть честные ограничения, о которых стоит знать заранее:

- Список виртуализирован: старые сообщения вымываются. В файле будет **только
  то, что произошло с момента старта записи**, а не вся история эфира.
- Если прокрутить колонку вверх, новые сообщения перестанут появляться. Если
  закрыть панель чата на странице — захват остановится. В режиме «Экран» чат при
  этом всё равно попадёт в кадр, просто не в `.jsonl`.
- У таких строк нет серверных `msgId`, а время берётся локальное — оно может
  отличаться от времени на сервере TikTok.

Второй путь — перехват WebSocket, который сама страница держит открытым для чата
— **теперь работает**, и приоритет у него: сообщения приходят с серверными
`msgId` и временем создания. Ставит его главный процесс:
`webContents.executeJavaScript(код, true)` попадает в основной мир страницы и не
подчиняется её политике безопасности. Это единственный способ, который здесь
сработал: инлайн-скрипт из preload блокировался (в `script-src` tiktok.com нет
`'unsafe-inline'`, а `appendChild` при этом не бросает исключение — скрипт
просто молча не выполняется), `contextBridge.executeInMainWorld` в Electron 33
**отсутствует**, а `window.postMessage` из основного мира не доставляется в
изолированный мир preload. Кадры уходят из основного мира в preload по мосту
`contextBridge.exposeInMainWorld('__tkmChat', …)` и оттуда отправляются сразу в
главный процесс — рендерер в этой цепочке не участвует.

Оба пути пишут в один файл и дедуплицируются: то, что пришло по сокету, не
дублируется из DOM-колонки. Если чат не пишется, в консоли главного процесса при
старте записи с чатом печатается `[live-chat] tap stats: {...}` — счётчики
`total` / `matched` / `messages` / `frames` прямо с перехваченной страницы:
`matched: 0` значит, что эфир открыт не на той странице, а `frames: 0` при
`matched > 0` — что сокет молчит. Те же значения доступны из консоли рендерера
через `window.api.live.wsStats()`.

Диагностика, если что-то пойдёт не так: счётчик «чата: N» в строке записи
обновляется раз в секунду. Если `.chat.jsonl` пуст, проверьте, что «Обзор»
открыт именно на этом эфире и панель чата не свёрнута.

## Стек и почему он

| Решение                                 | Причина                                                                                                                                                                                                          |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Electron                                | В песочнице сборки нет Rust, Tauri недоступен. Electron ставится через npm на обе платформы.                                                                                                                     |
| yt-dlp как sidecar                      | Единственный стабильно работающий с TikTok движок: 196k звёзд, форматы без watermark, `--proxy`, `--cookies-from-browser`. Качает байты: докачка, склейка, прогресс.                                             |

| Chromium-сетевой стек Electron для HTTP | Прокси (включая SOCKS5) и cookie jar уже настроены для встроенного браузера — не нужно дублировать туннелирование.                                                                                               |

## Как на самом деле работает скачивание (проверено 09.10.2026)

Замер на реальном видео (`yt-dlp --verbose`) показал важную вещь: **yt-dlp
вообще не обращается к мобильному API**. Он скачивает HTML-страницу
`www.tiktok.com` (407 КБ), разбирает `__UNIVERSAL_DATA_FOR_REHYDRATION__` и при
этом использует impersonation `chrome-146` через curl_cffi. Ни одного запроса к
`/aweme/v1/` в логе нет.

Отсюда следствия, которые стоит понимать до того, как что-то чинить:

- Успешная загрузка через yt-dlp **ничего не говорит** о доступности мобильного
  API.
- Мобильный API отдаёт пустой ответ (`empty-body`, с мая 2025 — [yt-dlp#13134]).
  Причина не установлена окончательно: серверная проверка подписей, блокировка
  по IP или отвержение TLS-отпечатка клиента. Все три варианта честно
  перечислены в тексте ошибки приложения.
- Встроенная X-Gnarly (веб-подпись, aid=1988) пустой ответ **не лечит** —
  проверено включением подписи, результат не изменился. Мобильному эндпоинту
  нужно семейство X-Gorgon/X-Ladon/X-Argus/X-Khronos, для него есть только
  опциональный Python sidecar.

Поэтому режим «Движок: авто» по умолчанию пробует API, а при отказе уходит на
рабочий маршрут yt-dlp. Скачивание работает; собственный клиент API оставлен как
диагностический инструмент и как точка входа для будущего мобильного подписанта.

Реверс X-Bogus / webmssdk сознательно не делался. Регистрация устройства тоже не
нужна: yt-dlp генерирует `device_id`/`cdid`/`openudid` локально из случайных
значений, вызовов `device_register` в его коде нет.

## Возможности

- **Скачать** — вставить ссылку, получить метаданные (автор, просмотры, лайки,
  список форматов), скачать видео / только обложку / только аудио.
- **Очередь загрузок** — параллельные задачи, прогресс-бар, отмена по одной или
  все сразу, кнопка «Показать» открывает файл в проводнике.
- **Автор** — ссылка на профиль → постраничная сетка видео из мобильного API
  (кнопка «Загрузить ещё» подгружает следующую страницу), скачивание по клику
  или «Скачать все». Фото-посты сохраняются целиком.
- **Обзор** — встроенный браузер (webview) на tiktok.com, использующий тот же
  прокси, что и загрузчик. **Правый клик по видео → «Скачать видео»** скачивает
  то, что сейчас играет в ленте. Кнопка «Скачать текущее видео» под лентой
  делает то же самое по кнопке.
- **Запись эфиров** — в нижней панели «Обзора», рядом с «Скачать текущее видео».
  Кнопка **«Запись трансляции»** пишет ту трансляцию, которую сейчас показывает
  встроенный браузер — ссылку вводить не нужно. Два режима: чистый поток через
  ffmpeg без перекодирования или «как на странице» (вместе с зрителями и чатом),
  и по галочке чат эфира в `.jsonl` и `.srt` рядом с видео. Подробности в
  разделе [«Запись эфиров»](#запись-эфиров).
- **Гео-обход** — состояние обхода: заявленный регион, оператор, таймзона,
  приложение, реальная страна по IP, вердикт о согласованности. Выбор профиля
  региона и оператора, показ полного набора параметров запроса, проверка на
  конкретном видео.
- **Настройки** — прокси, cookies из браузера или из файла, движок метаданных,
  регион, `ttwid`/`msToken`, часовой пояс, API host, App info, device ID,
  качество, лимит по высоте, папка загрузок, обложки, info.json, папка с
  бинарниками.

## Скачивание из ленты рекомендаций

Ссылка вида `https://www.tiktok.com/foryou` — это не видео, а страница ленты.
yt-dlp на такой URL отвечает `Unsupported URL`, а прежняя версия приложения
добавляла к этому своё `Не удалось извлечь ID видео из ссылки` — две ошибки
вместо одного понятного объяснения.

Сейчас ссылка классифицируется **до** запуска движка (`classifyUrl` в
`src/main/ytdlp.js`):

| Вид ссылки                                            | Что скажет приложение                             |
| ----------------------------------------------------- | ------------------------------------------------- |
| `/@user/video/123…`, `/@user/photo/123…`              | скачивается как обычно                            |
| `vm.tiktok.com/…`, `vt.tiktok.com/…`                  | короткая ссылка, редирект разрезолвит yt-dlp      |
| `/foryou`, `/`, `/following`, `/explore`, `/discover` | «это лента, а не видео» + переход в «Обзор»       |
| `/@user`                                              | «это профиль автора» + переход во вкладку «Автор» |
| `/tag/…`, `/music/…`                                  | «это хештег / звук»                               |
| не TikTok                                             | «это не ссылка TikTok»                            |

### Как гарантируется отсутствие водяного знака

Проверено на живом видео (`yt-dlp -J`, 11 форматов): **в выдаче нет ни одного
формата с водяным знаком**, а кадр из скачанного файла проверен визуально —
логотипа TikTok в нём нет. То есть в этом маршруте (web-страница →
`__UNIVERSAL_DATA_FOR_REHYDRATION__` → `bitrateInfo[].PlayAddr`) TikTok отдаёт
чистые ссылки.

Но при этом обнаружился настоящий баг: **фильтр водяного знака в приложении не
работал вообще.**

```bash
# было:
bestvideo[format_note!*=watermark]+bestaudio/best[format_note!*=watermark]/best
# yt-dlp 2026.08.19:
b[format_note!*=watermark]      -> ERROR: Requested format is not available
b[format_note!*=watermarked!]   -> падение с Python traceback
b[format_id!=download]          -> OK
```

Причина: у чистых форматов TikTok поля `format_note` вообще нет, а yt-dlp
считает отсутствующее поле несовпадением — то есть фильтр отбрасывал **все**
форматы. Вся цепочка падала, и срабатывал финальный голый `/best`, то есть
фактически выбирал yt-dlp сам по селектору по умолчанию. Фильтр не был выполнен
ни разу.

Теперь селектор такой:

```
bv*[format_id!=download][format_id^=h264]+ba / …[format_id!=download] / bv*[format_id!=download]
```

- исключение по `format_id!=download` — единственная рабочая проверка; водяной
  знак yt-dlp помечает именно как `format_id: download`, `preference: -2`
  (`yt_dlp/extractor/tiktok.py:634`);
- голого `/best` в конце нет: он охотно взял бы watermarked-вариант, когда тот
  есть (yt-dlp#9704);
- по умолчанию предпочитается **H.264**: TikTok отдаёт `bytevc1` = HEVC, который
  не везде играет, а `h264_540p_*` уже несёт наибольший битрейт. Переключается
  чекбоксом «Предпочитать HEVC».

Попутно исправлен ещё один баг: ограничение высоты было Fatal. Фильтр
`[height<=720]` отсекал вообще всё, потому что форматы с «540p» в названии
реально имеют `height=1024`/`1280`. Теперь ограничение применяется к отдельным
звеньям цепочки, а последнее звено идёт без него.

## Как скачать то, что сейчас играет

Самый быстрый способ: **правый клик прямо на видео в ленте** → меню «Скачать
видео». В меню также есть «Только аудио (MP3)» и «Скопировать ссылку». Кнопка
**«Скачать текущее видео»** делает то же самое для ролика, который играет прямо
сейчас.

Здесь есть важная техническая деталь, ради которой стоит объяснить. В ленте
элемент `<video>` отдаётся через Media Source Extensions, поэтому `video.src` —
это `blob:https://…`, который yt-dlp скачать не может (проверено: во всех
найденных OSS-проектах, которые делают так же, — `greasyfork 449644`,
`ShZhao27208/tikdownload` — сначала приходится превращать `blob` в обычный
HTTP-запрос, и это самая хрупкая часть). Приложение идёт сразу по надёжному
пути: находит `<video>` (играющий или под курсором), поднимается по DOM до
ближайшего якоря вида `a[href*="/video/"]` или атрибута `data-e2e-vid` и
получает канонический ID. Дальше работает обычный уже проверенный конвейер
загрузки: приоритет форматов без watermark, прогресс, отмена.

### Как определяется «то, что сейчас играет» (и почему это было сломано)

Симптом был такой: сколько ни нажимай «Скачать текущее видео», скачивается один
и тот же ролик. Причина — не в загрузчике, а в выборе ролика, и она характерна
именно для вертикальной ленты TikTok:

- все карточки одинакового размера и присутствуют в DOM одновременно (TikTok
  предзагружает соседние), поэтому ранжирование **по площади** даёт равные
  значения;
- сортировка при равенстве падает в порядок документа — и возвращает первый
  ролик, то есть всегда один и тот же;
- вторая половина баге была моей собственной: координаты правого клика
  подставлялись в исполняемый скрипт как **строки**, а скрипт проверял их через
  `typeof … === 'number'`. Проверка всегда давала `false`, то есть правый клик
  молча игнорировался и срабатывал запасной путь «что в середине экрана».

Поэтому выбор теперь трёхуровневый: реально **играющее** видео → самое
**видимое** → **ближайшее к центру экрана**; при правом клике координаты имеют
приоритет и подставляются числовыми литералами. Selftest фиксирует оба случая:
точка (50, 350) лежит вне перекрывающего блока и обязана вернуть ролик из него,
а выбор без координат обязан вернуть тот, что в середине экрана, а не первый в
DOM.

Правый клик перехватывается **preload'ом гостевой страницы**
(`src/preload/webview-preload.js`), а не обработчиком в приложении: DOM-событие
`context-menu` на `<webview>` в Electron 33 не приходит вовсе (измерено — 0
срабатываний), а меню «Загрузить видео / Скорость / Качество» рисует сам плеер
TikTok. Preload загружается до скриптов страницы и гасит **только** действие по
умолчанию — нативное меню Chromium; проброс события он не прерывает, поэтому
собственное меню TikTok рисуется как обычно. Своего меню приложение на правый
клик не строит вообще: его виджет рисует браузерный процесс через Chromium
Views, у него нет DOM-узла, и скрыть его скриптами страницы невозможно (четыре
попытки, все безуспешны). Selftest проверяет это настоящим правым кликом по
`<video>` внутри `<webview>` и требует, чтобы отчёт preload'а дошёл до main и
был опознан как клик по видео.

Заодно приложение **не даёт скачать не то**: если в очередь попадёт ссылка не на
конкретный ролик (профиль, лента, хештег, прямая CDN-ссылка), задача не
создаётся, а показывается явное сообщение — иначе yt-dlp скачал бы «первый ролик
со страницы», и все задачи сохранили бы один и тот же файл. В карточке задачи
виден и сам URL.

Что взято из OSS:

| Решение                                                                                | Откуда                                                                                                       |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| привязка `<video>` к ID через ближайший `a[href]` / `data-e2e-vid`                     | `ShZhao27208/tikdownload` (`content.js:getVidFromElement`)                                                   |
| `blob:` в ленте — тупик, нужен id, а не src                                            | `greasyfork 449644` (аварийный `videoTag.src` + `blob`)                                                      |
| без водяного знака — `playAddr` / `bitrateInfo[].PlayAddr`, **никогда** `downloadAddr` | `yt-dlp tiktok.py`, `cobalt`                                                                                 |
| SSR-JSON ленты неполон, для «текущего» видео нужен id из DOM                           | `cobalt`, `you-get`, `yt-dlp` — все читают `__UNIVERSAL_DATA_FOR_REHYDRATION__`, но только на странице видео |

### Откуда берутся видео из ленты (массовый сбор)

Публичного эндпоинта «дай мою ленту рекомендаций» у TikTok нет: лента
персонализирована и отдаётся только реальному браузеру. Поэтому для массовой
загрузки видео собираются из DOM уже открытой страницы — того самого Chromium, у
которого есть прокси, cookies и отпечаток соединения пользователя. Страница сама
решает, что показать; сборщик лишь превращает видимое в список
(`src/main/feed.js`).

Как пользоваться:

1. Вкладка **«Обзор»** → открыть `tiktok.com/foryou` (или «Подписки»,
   «Рекомендуемые»), дождаться загрузки ленты и при необходимости прокрутить
   вручную.
2. **«Собрать видео из ленты»** — появляется сетка карточек с обложкой,
   заголовком и просмотрами. Каждая карточка — обычная ссылка на видео, клик
   ставит её в очередь.
3. **«Догрузить ещё»** — скроллит страницу и добавляет новые видео к уже
   собранным (список растёт, а не заменяется).
4. **«Скачать всё»** — ставит в очередь все собранные видео разом; фото-посты
   (они помечены бейджем) скачиваются целиком из вкладки «Скачать».

Если страница пустая, скорее всего лента не отрисовалась: нужен интернет через
прокси и, для некоторых аккаунтов, авторизация.

## Открывается «Обзор»

При запуске открывается вкладка **«Обзор»** с лентой рекомендаций, а не
«Скачать». Встроенный браузер монтируется сразу при старте, чтобы страница
грузилась параллельно с остальной инициализацией, а не по клику пользователя.

Из-за этого пришлось разобраться с `allowpopups` у `<webview>`. Атрибут нужен:
без него ни `target=_blank`, ни `window.open()` не доходят ни до одного
обработчика — измерено, 0 событий. При этом Electron печатает предупреждение
«popups are just BrowserWindows». Оно не считается ошибкой в selftest, потому
что это осознанное решение, а не баг.

Попутно нашёлся настоящий баг: DOM-событие `new-window` на элементе `<webview>`
в Electron 33 **не приходит вовсе** (0 срабатываний на двух разных триггерах),
поэтому ссылки, открываемые в новой вкладке, молча не доходили до системного
браузера. Обработка перенесена на `setWindowOpenHandler` гостевой страницы
(`app.on('web-contents-created')` + проверка `getType() === 'webview'`).

## Обход региональных ограничений

### Что делает TikTokModCloud и почему его механика не переносится как есть

TikTokModCloud — закрытый модифицированный клиент для Android, распространяемый
через Telegram-канал; исходного кода в открытых источниках нет. Обход региона в
нём **не собственный**: он реализован в отдельном Xposed-модуле
[`eXtreames/UnleashedTikTok`](https://github.com/eXtreames/UnleashedTikTok), чей
README прямо говорит, что модуль работает _поверх_ TikTokModCloud («Works with
official TikTok and popular third-party mods»).

Вся механика — шесть строк в `RegionBypass.java`:

```java
REGION_COUNTRY_ISO    = "BY";      // Беларусь
REGION_OPERATOR_NUM   = "25704";   // MCC+MNC оператора life:) )
REGION_OPERATOR_NAME  = "life:)";
getSimCountryIso / getNetworkCountryIso  -> "BY"
getSimOperator   / getNetworkOperator    -> "25704"
```

Модуль подменяет ответы `android.telephony.TelephonyManager`, поэтому
официальный APK TikTok считает, что телефон в Беларуси. На десктопе таких
вызовов нет, и перенести хуки буквально невозможно.

### Что сделано в этом приложении

Та же идея перенесена на сетевой уровень: мобильный API TikTok принимает те же
факты параметрами запроса. Приложение отправляет `POST` на
`/aweme/v1/multi/aweme/detail/` с параметрами `region`, `current_region`,
`sys_region`, `residence`, `carrier_region`, `op_region`, `mcc_mnc`,
`timezone_name`, `timezone_offset`, `language`, `app_info`, `iid`, `device_id`,
плюс мобильный User-Agent — то есть заявляет то же самое устройство, что описал
бы SIM-хук.

Подпись запросов, судя по коду yt-dlp, не требуется: `_extract_aweme_app`
отправляет пустой заголовок `X-Argus` и ждёт ответа. Но проверить это на живом
ответе нельзя — yt-dlp на практике идёт webpage-маршрутом (см. раздел выше) и в
мобильный API не заходит. Поэтому реверс X-Bogus/X-Dynosaur/webmssdk не делался,
а встроенная X-Gnarly оставлена необязательной: она ничего не ломает и не
помогает, пока мобильный API отвечает пустым телом.

Профили регионов (`src/main/regions.js`) содержат 19 стран с реальными MCC/MNC
операторов. Профиль `BY` — `life:)` / `25704` / `Europe/Minsk` — точно
воспроизводит значения оригинального модуля.

### Почему этого одного недостаточно

Подмена региона меняет то, что приложение сообщает о себе. Настоящая причина
сообщения «TikTok показывает только старые видео» — реальный IP подключения:
сервер применяет региональные ограничения по адресу, а не по заголовкам. Поэтому
прокси в выбранной стране остаётся обязательной частью схемы, а не
рекомендацией.

Вкладка **«Гео-обход»** сравнивает заявленный регион с реальной страной по IP и
прямо показывает рассогласование, если оно есть, вместо того чтобы молча
отдавать пустую выдачу.

### Порядок, который реально работает

1. **Прокси обязателен.** IP датацентров и многие домашние IP в блок-листе
   TikTok. Поддерживаются `http`, `https`, `socks5`, `socks5h`, например
   `socks5://127.0.0.1:1080`. Прокси применяется и к загрузчику, и ко
   встроенному браузеру (`session.setProxy`).
2. **Регион подбирается под прокси** на вкладке «Гео-обход». Регион, оператор,
   часовой пояс и язык берутся из одного профиля и не противоречат друг другу.
3. **Cookies из браузера** (`chrome`, `firefox`, `edge`, `brave`, `opera`,
   `safari`) или свой файл cookies в формате Netscape — если TikTok требует
   вход, подтверждение возраста или аккаунт для региона.
4. **Эмулируемое устройство закрепляется** при первом запуске и
   переиспользуется: постоянный `device_id`/`iid` нужен, потому что TikTok
   реагирует на смену устройства.

### Исправленная ошибка в движке

yt-dlp отправляет регион жёстко зашитым в `US` (`current_region`, `sys_region`,
`residence`, `carrier_region`, `op_region`, `timezone_name=America/New_York`), а
через `--extractor-args` это не переопределяется — там доступны только
`api_hostname`, `app_info`, `device_id`. Поэтому файлы по-прежнему качает
yt-dlp, а метаданные и списки по умолчанию получает собственный клиент
(`Движок метаданных: Авто`).

Отдельно устранена ошибка, из-за которой приложение само выключало рабочий путь:
при пустом `apiHostname` в аргументы уходило
`tiktok:api_hostname=www.tiktok.com`, то есть yt-dlp переключался с мобильного
API (работает без подписи) на веб-путь (требует подписи, чаще упирается в
геоблок). Теперь при пустом значении параметр не передаётся вовсе и используется
мобильный хост по умолчанию.

### Проверка

Кнопка **«Проверить»** на вкладке «Гео-обход» прогоняет реальный запрос и
показывает, какой движок ответил и какое разрешение вернулось. **Справка →
Диагностика окружения** печатает заявленный регион, оператора, таймзону,
`device_id` и реальную страну IP. Чекбокс «Показать параметры запроса» выводит
полный набор уходящих параметров — удобно для отладки конкретной комбинации.

## Запуск из исходников

```bash
npm install          # тянет Electron и бинарники в vendor/bin
npm start            # запуск
npm run dev          # запуск с devtools
npm run dist:win     # NSIS + portable .exe
npm run dist:linux   # AppImage + .deb + tar.gz
```

Требуется Node.js 18+.

`npm install` дополнительно скачивает `yt-dlp` и `ffmpeg` в `vendor/bin` — эта
папка в репозиторий не попадает, в репозитории лежит только `vendor/x-gnarly`.
Собирать дистрибутив нужно после `npm install`, иначе в сборку не попадут
бинарники.

Скачиваются они под архитектуру машины, на которой идёт `npm install`: на Linux
это `yt-dlp_linux` и статический `ffmpeg` из tar.xz (распаковывается системным
`tar`), на Windows — `.exe`-сборки тех же программ.

Если npm 11+ блокирует скрипты установки зависимостей, разрешение на `electron`
уже прописано в `package.json` в поле `allowScripts`. Если всё же заблокировал —
`npm install-scripts approve electron`.

### Сборка `.deb` без `libcrypt.so.1`

`.deb` electron-builder собирает через `fpm` со встроенным Ruby, которому нужен
`libcrypt.so.1`: на Manjaro его даёт `libxcrypt-compat`, на Ubuntu —
`libcrypt1`. AppImage и `tar.gz` от него не зависят и собираются в любом случае.
В CI зависимость ставится явно.

### Диагностика

Меню **Справка → Диагностика окружения** показывает пути к yt-dlp/ffmpeg,
активный прокси, регион и cookies. **Справка → Обновить yt-dlp** обновляет
движок на месте.

## Автономный selftest

```bash
npx electron . --selftest
```

Поднимает локальный HTTP-сервер с 3 МБ данных и прогоняет весь путь загрузки:
сборка аргументов, парсинг `PROG`-прогресса, шаблон вывода, создание папки,
чтение размера файла. Это не зависит от доступности TikTok с машины сборки.

```json
{ "done": true, "size": 3145728, "sizeOnDisk": 3145728, "progressSeen": true }
```

Дополнительно проверяется слой обхода региона: что в профиле `BY` стоят именно
`life:)` / `25704` / `Europe/Minsk` / UTC+3, что все шесть полей региона
(`region`, `current_region`, `sys_region`, `residence`, `carrier_region`,
`op_region`) уходят в запрос как `BY`, что идентификатор устройства стабилен
между вызовами, что рассогласование IP и региона обнаруживается, и что yt-dlp не
переключается на подписанный веб-хост по умолчанию.

Также проверяются классификатор ссылок (9 кейсов: видео, короткая ссылка, лента,
профиль, хештег, звук, чужой сайт, пустая строка), отказ `probe` для ссылки на
ленту с кодом `unsupported-url`, сбор видео с локальной страницы, имитирующей
TikTok (три уникальных видео из пяти якорей — с дублем и не-видео ссылкой,
сохранение накопленного списка при повторном сборе и рабочий скролл контейнера),
а также определение текущего видео: `<video>` с **blob-** источником (как в
настоящей ленте) корректно превращается в каноническую ссылку
`https://www.tiktok.com/@now.user/video/7000000000000000009` — и по текущему
играющему ролику, и по координатам правого клика.

Отдельно проверяется обработка ссылок, открываемых в новой вкладке: фикстура с
настоящими синтетическими кликами (не через `executeJavaScript` — у него нет
user activation, и блокировщик всплывающих окон его отбивает) внутри
`<webview allowpopups>`. Проверка требует, чтобы гостевой странице доставили оба
запроса — и она нужна, чтобы никто не «починил» предупреждение Electron
удалением `allowpopups` и не сломал при этом внешние ссылки.

Селектор формата проверяется отдельно: ни в одном его звене не должно быть
фильтра по `format_note` (он отбрасывает все чистые форматы), каждое звено
обязано содержать `format_id!=download`, в конце не должно оставаться голого
`/best`, а ограничение высоты не должно стоять в последнем звене — иначе любой
лимит молча ломает загрузку.

## Где берутся yt-dlp и ffmpeg

`scripts/postinstall.js` кладёт их в `vendor/bin`. Эта папка не коммитится — она
platform-specific и пересоздаётся командой выше, — поэтому в клонированном
репозитории её нет, а в собранном дистрибутиве она появляется через
`extraResources`. Если загрузка бинарника не удалась, приложение работает и без
них: фолбэк на `PATH`, а настройка «Папка с yt-dlp / ffmpeg» позволяет указать
путь вручную.

От того, что скачалось на машине сборщика, пакет не зависит: хук
`scripts/before-pack.js` вычищает из `vendor/bin` бинарники чужих платформ,
иначе Linux-пакет унёс бы с собой мёртвый `yt-dlp.exe`, а Windows — `yt-dlp`.

`ffprobe` намеренно не поставляется: приложение его нигде не запускает — в
диагностике показывается путь, только если бинарник есть в системе, — а
статическая сборка весит ещё 80 МБ. Запись эфиров и склейка форматов идут через
один `ffmpeg`.

### Почему ffmpeg проверяется перед использованием

Запись эфира в режиме «Поток» — это ffmpeg на подписанном CDN-адресе TikTok.
Если бинарник не может открыть сетевой адрес, файл получается пустым, и
пользователю показывается «поток не отдал ни одного кадра» — вина, которая на
самом деле не в TikTok.

Такое и случилось: статическая сборка ffmpeg 7.0.2 (johnvansickle, glibc 2.19) в
статике не умеет резолвить имена — нет NSS-модулей, и процесс падает с SIGSEGV
на **любом** сетевом вводе, включая обычный `http://` на локальный сервер.
Проверено на Manjaro: тот же адрес через системный ffmpeg писал мегабайты,
вложенный — ноль байт и падение.

Поэтому теперь:

- `scripts/postinstall.js` после скачивания проверяет бинарник запросом к
  заведомо несуществующему имени в зарезервированной зоне `.invalid` (ни один
  запрос в интернет не уходит) и **выбрасывает** бинарник, если тот падает.
- `src/main/binaries.js` при выборе ffmpeg проверяет каждый кандидат и, если
  вложенный бинарник нерабочий, берёт следующий — системный.
- Источник заменён на сборки BtbN/FFmpeg-Builds: они линкуются с системной
  glibc, поэтому резолвер работает.

Проверка занимает ~150 мс и выполняется один раз за запуск.

`vendor/x-gnarly` — единственная часть `vendor/`, которая **коммитится**: это 11
КБ исходников на JS со своей лицензией MIT, и без них слой подписей
(`src/main/signer.js`) не запустится.

## Структура

```
src/main/main.js       окно, меню, IPC, прокси для сессии, selftest
src/main/ttapi.js      клиент мобильного API TikTok с подменой региона
src/main/regions.js    профили регионов: операторы (MCC/MNC), таймзоны, языки, app_info
src/main/geo.js        определение страны по IP и проверка согласованности с регионом
src/main/engine.js     выбор движка: мобильный API с откатом на yt-dlp
src/main/feed.js       сбор видео из отрисованной страницы webview (лента рекомендаций)
src/main/signer.js     слой подписей: X-Gnarly (встроенный) + опциональный Python sidecar
src/main/ytdlp.js      аргументы, загрузка, очередь, прогресс, отмена, маппинг ошибок,
                       классификация ссылок (видео / лента / профиль / хештег / звук)
src/main/binaries.js   поиск yt-dlp/ffmpeg: override → vendor/bin → PATH
src/main/settings.js   настройки в userData/settings.json, SCHEMA_VERSION + raw() для миграций
src/preload/preload.js contextBridge, без nodeIntegration
src/preload/webview-preload.js preload гостя: перехват правого клика, гашение меню страницы
src/renderer/          UI: index.html, styles.css, renderer.js
scripts/postinstall.js загрузка бинарников
vendor/x-gnarly/       вендоренный encode.js/decode.js (MIT, justscrapeme) — в репозитории
vendor/bin/            yt-dlp и ffmpeg — не в репозитории, скачивает postinstall
```

`vendor/` попадает в сборку через `extraResources`, поэтому и `binaries.js`, и
`signer.js` ищут файлы по списку корней (dev: `<repo>/vendor/...`, packaged:
`<resources>/vendor/...`) через `setResourcesRoot()`, а не по одному жёсткому
пути от `__dirname` — иначе в packaged-сборке путь указывал бы внутрь
`app.asar`, где `vendor/` нет.
