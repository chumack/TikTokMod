# TikTokMod

Кроссплатформенное десктоп-приложение для Windows и Linux: встроенный браузер TikTok,
скачивание видео (приоритет форматов без watermark), массовая загрузка по ссылке на
профиль автора и настройки маршрутизации трафика для обхода региональных ограничений.

## Установка

Текущая версия — **0.2.1**.

Установщик для Windows: `TikTokMod Setup 0.2.1.exe`.

- Установка **для всех пользователей** — установщик запрашивает права администратора.
  Папка по умолчанию — `C:\Program Files\TikTokMod`; на странице установки её можно
  заменить на любую другую.
- **Никаких чужих учётных данных в сборке нет.** Настройки, cookies и сессия
  встроенного браузера хранятся в профиле пользователя (`%APPDATA%\tiktok-mod` на
  Windows) и создаются с нуля при первом запуске. Входите в свой аккаунт TikTok сами —
  через вкладку «Обзор» или раздел «Настройки».
- Удаление программы удаляет и профиль: cookies, настройки и кэш исчезают, при
  следующей установке приложение снова открывается чистым. Чтобы сохранить профиль,
  удалите папку `C:\Program Files\TikTokMod` вручную, не запуская деинсталлятор.

Для тех, кому установка не нужна, есть portable-сборка `TikTokMod 0.2.1.exe` —
запускается напрямую, ничего не регистрируя в системе.

> Версия 0.1.0 ставилась только для текущего пользователя, а 0.2.x — для всех.
> Это разные записи в реестре, поэтому перед установкой 0.2.x удалите 0.1.0 через
> «Параметры → Приложения», иначе обе копии останутся на машине.

## Стек и почему он

| Решение | Причина |
|---|---|
| Electron | В песочнице сборки нет Rust, Tauri недоступен. Electron ставится через npm на обе платформы. |
| yt-dlp как sidecar | Единственный стабильно работающий с TikTok движок: 196k звёзд, форматы без watermark, `--proxy`, `--cookies-from-browser`. Качает байты: докачка, склейка, прогресс. |
| Собственный клиент мобильного API | Метаданные и списки: yt-dlp жёстко зашивает регион `US` и не даёт его менять. Сейчас отвечает пустым телом (см. раздел ниже) — работает как диагностика и как точка подключения подписанта, с откатом на yt-dlp. |
| Chromium-сетевой стек Electron для HTTP | Прокси (включая SOCKS5) и cookie jar уже настроены для встроенного браузера — не нужно дублировать туннелирование. |
| Нативный JS, без сборщика | UI на plain JS/CSS — нет цепочки webpack/vite, сборка дистрибутива не ломается. |
| ffmpeg | Нужен только для склейки раздельных видео+аудио потоков. Опционален. |

## Как на самом деле работает скачивание (проверено 09.10.2026)

Замер на реальном видео (`yt-dlp --verbose`) показал важную вещь: **yt-dlp вообще не
обращается к мобильному API**. Он скачивает HTML-страницу `www.tiktok.com`
(407 КБ), разбирает `__UNIVERSAL_DATA_FOR_REHYDRATION__` и при этом использует
impersonation `chrome-146` через curl_cffi. Ни одного запроса к `/aweme/v1/` в логе нет.

Отсюда следствия, которые стоит понимать до того, как что-то чинить:

- Успешная загрузка через yt-dlp **ничего не говорит** о доступности мобильного API.
- Мобильный API отдаёт пустой ответ (`empty-body`, с мая 2025 — [yt-dlp#13134]).
  Причина не установлена окончательно: серверная проверка подписей, блокировка по IP
  или отвержение TLS-отпечатка клиента. Все три варианта честно перечислены в тексте
  ошибки приложения.
- Встроенная X-Gnarly (веб-подпись, aid=1988) пустой ответ **не лечит** — проверено
  включением подписи, результат не изменился. Мобильному эндпоинту нужно семейство
  X-Gorgon/X-Ladon/X-Argus/X-Khronos, для него есть только опциональный Python sidecar.

Поэтому режим «Движок: авто» по умолчанию пробует API, а при отказе уходит на рабочий
маршрут yt-dlp. Скачивание работает; собственный клиент API оставлен как диагностический
инструмент и как точка входа для будущего мобильного подписанта.

Реверс X-Bogus / webmssdk сознательно не делался. Регистрация устройства тоже не нужна:
yt-dlp генерирует `device_id`/`cdid`/`openudid` локально из случайных значений, вызовов
`device_register` в его коде нет.

## Возможности

- **Скачать** — вставить ссылку, получить метаданные (автор, просмотры, лайки, список
  форматов), скачать видео / только обложку / только аудио.
- **Очередь загрузок** — параллельные задачи, прогресс-бар, отмена по одной или все сразу,
  кнопка «Показать» открывает файл в проводнике.
- **Автор** — ссылка на профиль → постраничная сетка видео из мобильного API
  (кнопка «Загрузить ещё» подгружает следующую страницу), скачивание по клику или
  «Скачать все». Фото-посты сохраняются целиком.
- **Обзор** — встроенный браузер (webview) на tiktok.com, использующий тот же прокси,
  что и загрузчик. **Правый клик по видео → «Скачать видео»** скачивает то, что сейчас
  играет в ленте. «Скачать видео со страницы» подхватывает текущий URL, а панель
  «Скачивание из ленты» превращает любую открытую страницу в список карточек для
  массовой загрузки.
- **Гео-обход** — состояние обхода: заявленный регион, оператор, таймзона, приложение,
  реальная страна по IP, вердикт о согласованности. Выбор профиля региона и оператора,
  показ полного набора параметров запроса, проверка на конкретном видео.
- **Настройки** — прокси, cookies из браузера или из файла, движок метаданных, регион,
  `ttwid`/`msToken`, часовой пояс, API host, App info, device ID, качество, лимит по
  высоте, папка загрузок, обложки, info.json, папка с бинарниками.

## Скачивание из ленты рекомендаций

Ссылка вида `https://www.tiktok.com/foryou` — это не видео, а страница ленты. yt-dlp на
такой URL отвечает `Unsupported URL`, а прежняя версия приложения добавляла к этому своё
`Не удалось извлечь ID видео из ссылки` — две ошибки вместо одного понятного объяснения.

Сейчас ссылка классифицируется **до** запуска движка (`classifyUrl` в
`src/main/ytdlp.js`):

| Вид ссылки | Что скажет приложение |
|---|---|
| `/@user/video/123…`, `/@user/photo/123…` | скачивается как обычно |
| `vm.tiktok.com/…`, `vt.tiktok.com/…` | короткая ссылка, редирект разрезолвит yt-dlp |
| `/foryou`, `/`, `/following`, `/explore`, `/discover` | «это лента, а не видео» + переход в «Обзор» |
| `/@user` | «это профиль автора» + переход во вкладку «Автор» |
| `/tag/…`, `/music/…` | «это хештег / звук» |
| не TikTok | «это не ссылка TikTok» |

### Как гарантируется отсутствие водяного знака

Проверено на живом видео (`yt-dlp -J`, 11 форматов): **в выдаче нет ни одного формата с
водяным знаком**, а кадр из скачанного файла проверен визуально — логотипа TikTok в нём
нет. То есть в этом маршруте (web-страница → `__UNIVERSAL_DATA_FOR_REHYDRATION__` →
`bitrateInfo[].PlayAddr`) TikTok отдаёт чистые ссылки.

Но при этом обнаружился настоящий баг: **фильтр водяного знака в приложении не работал
вообще.**

```bash
# было:
bestvideo[format_note!*=watermark]+bestaudio/best[format_note!*=watermark]/best
# yt-dlp 2026.08.19:
b[format_note!*=watermark]      -> ERROR: Requested format is not available
b[format_note!*=watermarked!]   -> падение с Python traceback
b[format_id!=download]          -> OK
```

Причина: у чистых форматов TikTok поля `format_note` вообще нет, а yt-dlp считает
отсутствующее поле несовпадением — то есть фильтр отбрасывал **все** форматы. Вся цепочка
падала, и срабатывал финальный голый `/best`, то есть фактически выбирал yt-dlp сам по
селектору по умолчанию. Фильтр не был выполнен ни разу.

Теперь селектор такой:

```
bv*[format_id!=download][format_id^=h264]+ba / …[format_id!=download] / bv*[format_id!=download]
```

- исключение по `format_id!=download` — единственная рабочая проверка; водяной знак
  yt-dlp помечает именно как `format_id: download`, `preference: -2`
  (`yt_dlp/extractor/tiktok.py:634`);
- голого `/best` в конце нет: он охотно взял бы watermarked-вариант, когда тот есть
  (yt-dlp#9704);
- по умолчанию предпочитается **H.264**: TikTok отдаёт `bytevc1` = HEVC, который
  не везде играет, а `h264_540p_*` уже несёт наибольший битрейт. Переключается
  чекбоксом «Предпочитать HEVC».

Попутно исправлен ещё один баг: ограничение высоты было Fatal. Фильтр
`[height<=720]` отсекал вообще всё, потому что форматы с «540p» в названии реально
имеют `height=1024`/`1280`. Теперь ограничение применяется к отдельным звеньям цепочки,
а последнее звено идёт без него.

## Как скачать то, что сейчас играет

Самый быстрый способ: **правый клик прямо на видео в ленте** → меню «Скачать видео».
В меню также есть «Только аудио (MP3)» и «Скопировать ссылку». Кнопка **«Скачать текущее
видео»** делает то же самое для ролика, который играет прямо сейчас.

Здесь есть важная техническая деталь, ради которой стоит объяснить. В ленте элемент
`<video>` отдаётся через Media Source Extensions, поэтому `video.src` — это `blob:https://…`,
который yt-dlp скачать не может (проверено: во всех найденных OSS-проектах, которые
делают так же, — `greasyfork 449644`, `ShZhao27208/tikdownload` — сначала приходится
превращать `blob` в обычный HTTP-запрос, и это самая хрупкая часть). Приложение идёт
сразу по надёжному пути: находит `<video>` (играющий или под курсором), поднимается по
DOM до ближайшего якоря вида `a[href*="/video/"]` или атрибута `data-e2e-vid` и получает
канонический ID. Дальше работает обычный уже проверенный конвейер загрузки: приоритет
форматов без watermark, прогресс, отмена.

### Как определяется «то, что сейчас играет» (и почему это было сломано)

Симптом был такой: сколько ни нажимай «Скачать текущее видео», скачивается один и тот же
ролик. Причина — не в загрузчике, а в выборе ролика, и она характерна именно для
вертикальной ленты TikTok:

- все карточки одинакового размера и присутствуют в DOM одновременно (TikTok
  предзагружает соседние), поэтому ранжирование **по площади** даёт равные значения;
- сортировка при равенстве падает в порядок документа — и возвращает первый ролик,
  то есть всегда один и тот же;
- вторая половина баге была моей собственной: координаты правого клика подставлялись в
  исполняемый скрипт как **строки**, а скрипт проверял их через `typeof … === 'number'`.
  Проверка всегда давала `false`, то есть правый клик молча игнорировался и срабатывал
  запасной путь «что в середине экрана».

Поэтому выбор теперь трёхуровневый: реально **играющее** видео → самое **видимое** →
**ближайшее к центру экрана**; при правом клике координаты имеют приоритет и подставляются
числовыми литералами. Selftest фиксирует оба случая: точка (50, 350) лежит вне
перекрывающего блока и обязана вернуть ролик из него, а выбор без координат обязан вернуть
тот, что в середине экрана, а не первый в DOM.

Правый клик перехватывается **preload'ом гостевой страницы**
(`src/preload/webview-preload.js`), а не обработчиком в приложении: DOM-событие
`context-menu` на `<webview>` в Electron 33 не приходит вовсе (измерено — 0 срабатываний),
а меню «Загрузить видео / Скорость / Качество» рисует сам плеер TikTok. Preload загружается
до скриптов страницы и гасит **только** действие по умолчанию — нативное меню Chromium;
проброс события он не прерывает, поэтому собственное меню TikTok рисуется как обычно.
Своего меню приложение на правый клик не строит вообще: его виджет рисует браузерный
процесс через Chromium Views, у него нет DOM-узла, и скрыть его скриптами страницы
невозможно (четыре попытки, все безуспешны). Selftest проверяет это настоящим правым
кликом по `<video>` внутри `<webview>` и требует, чтобы отчёт preload'а дошёл до main и был
опознан как клик по видео.

Заодно приложение **не даёт скачать не то**: если в очередь попадёт ссылка не на
конкретный ролик (профиль, лента, хештег, прямая CDN-ссылка), задача не создаётся, а
показывается явное сообщение — иначе yt-dlp скачал бы «первый ролик со страницы», и все
задачи сохранили бы один и тот же файл. В карточке задачи виден и сам URL.

Что взято из OSS:

| Решение | Откуда |
|---|---|
| привязка `<video>` к ID через ближайший `a[href]` / `data-e2e-vid` | `ShZhao27208/tikdownload` (`content.js:getVidFromElement`) |
| `blob:` в ленте — тупик, нужен id, а не src | `greasyfork 449644` (аварийный `videoTag.src` + `blob`) |
| без водяного знака — `playAddr` / `bitrateInfo[].PlayAddr`, **никогда** `downloadAddr` | `yt-dlp tiktok.py`, `cobalt` |
| SSR-JSON ленты неполон, для «текущего» видео нужен id из DOM | `cobalt`, `you-get`, `yt-dlp` — все читают `__UNIVERSAL_DATA_FOR_REHYDRATION__`, но только на странице видео |

### Откуда берутся видео из ленты (массовый сбор)

Публичного эндпоинта «дай мою ленту рекомендаций» у TikTok нет: лента персонализирована
и отдаётся только реальному браузеру. Поэтому для массовой загрузки видео собираются из
DOM уже открытой страницы — того самого Chromium, у которого есть прокси, cookies и
отпечаток соединения пользователя. Страница сама решает, что показать; сборщик лишь
превращает видимое в список (`src/main/feed.js`).

Как пользоваться:

1. Вкладка **«Обзор»** → открыть `tiktok.com/foryou` (или «Подписки», «Рекомендуемые»),
   дождаться загрузки ленты и при необходимости прокрутить вручную.
2. **«Собрать видео из ленты»** — появляется сетка карточек с обложкой, заголовком и
   просмотрами. Каждая карточка — обычная ссылка на видео, клик ставит её в очередь.
3. **«Догрузить ещё»** — скроллит страницу и добавляет новые видео к уже собранным
   (список растёт, а не заменяется).
4. **«Скачать всё»** — ставит в очередь все собранные видео разом; фото-посты
   (они помечены бейджем) скачиваются целиком из вкладки «Скачать».

Если страница пустая, скорее всего лента не отрисовалась: нужен интернет через прокси
и, для некоторых аккаунтов, авторизация.

## Открывается «Обзор»

При запуске открывается вкладка **«Обзор»** с лентой рекомендаций, а не «Скачать».
Встроенный браузер монтируется сразу при старте, чтобы страница грузилась параллельно с
остальной инициализацией, а не по клику пользователя.

Из-за этого пришлось разобраться с `allowpopups` у `<webview>`. Атрибут нужен: без него
ни `target=_blank`, ни `window.open()` не доходят ни до одного обработчика — измерено,
0 событий. При этом Electron печатает предупреждение «popups are just BrowserWindows».
Оно не считается ошибкой в selftest, потому что это осознанное решение, а не баг.

Попутно нашёлся настоящий баг: DOM-событие `new-window` на элементе `<webview>` в
Electron 33 **не приходит вовсе** (0 срабатываний на двух разных триггерах), поэтому
ссылки, открываемые в новой вкладке, молча не доходили до системного браузера.
Обработка перенесена на `setWindowOpenHandler` гостевой страницы
(`app.on('web-contents-created')` + проверка `getType() === 'webview'`).

## Обход региональных ограничений

### Что делает TikTokModCloud и почему его механика не переносится как есть

TikTokModCloud — закрытый модифицированный клиент для Android, распространяемый через
Telegram-канал; исходного кода в открытых источниках нет. Обход региона в нём **не
собственный**: он реализован в отдельном Xposed-модуле
[`eXtreames/UnleashedTikTok`](https://github.com/eXtreames/UnleashedTikTok), чей README
прямо говорит, что модуль работает *поверх* TikTokModCloud («Works with official TikTok
and popular third-party mods»).

Вся механика — шесть строк в `RegionBypass.java`:

```java
REGION_COUNTRY_ISO    = "BY";      // Беларусь
REGION_OPERATOR_NUM   = "25704";   // MCC+MNC оператора life:) )
REGION_OPERATOR_NAME  = "life:)";
getSimCountryIso / getNetworkCountryIso  -> "BY"
getSimOperator   / getNetworkOperator    -> "25704"
```

Модуль подменяет ответы `android.telephony.TelephonyManager`, поэтому официальный APK
TikTok считает, что телефон в Беларуси. На десктопе таких вызовов нет, и перенести хуки
буквально невозможно.

### Что сделано в этом приложении

Та же идея перенесена на сетевой уровень: мобильный API TikTok принимает те же факты
параметрами запроса. Приложение отправляет `POST` на `/aweme/v1/multi/aweme/detail/`
с параметрами `region`, `current_region`, `sys_region`, `residence`, `carrier_region`,
`op_region`, `mcc_mnc`, `timezone_name`, `timezone_offset`, `language`, `app_info`,
`iid`, `device_id`, плюс мобильный User-Agent — то есть заявляет то же самое
устройство, что описал бы SIM-хук.

Подпись запросов, судя по коду yt-dlp, не требуется: `_extract_aweme_app` отправляет пустой
заголовок `X-Argus` и ждёт ответа. Но проверить это на живом ответе нельзя — yt-dlp на
практике идёт webpage-маршрутом (см. раздел выше) и в мобильный API не заходит. Поэтому
реверс X-Bogus/X-Dynosaur/webmssdk не делался, а встроенная X-Gnarly оставлена
необязательной: она ничего не ломает и не помогает, пока мобильный API отвечает пустым
телом.

Профили регионов (`src/main/regions.js`) содержат 19 стран с реальными MCC/MNC
операторов. Профиль `BY` — `life:)` / `25704` / `Europe/Minsk` — точно воспроизводит
значения оригинального модуля.

### Почему этого одного недостаточно

Подмена региона меняет то, что приложение сообщает о себе. Настоящая причина сообщения
«TikTok показывает только старые видео» — реальный IP подключения: сервер применяет
региональные ограничения по адресу, а не по заголовкам. Поэтому прокси в выбранной
стране остаётся обязательной частью схемы, а не рекомендацией.

Вкладка **«Гео-обход»** сравнивает заявленный регион с реальной страной по IP и прямо
показывает рассогласование, если оно есть, вместо того чтобы молча отдавать пустую
выдачу.

### Порядок, который реально работает

1. **Прокси обязателен.** IP датацентров и многие домашние IP в блок-листе TikTok.
   Поддерживаются `http`, `https`, `socks5`, `socks5h`, например `socks5://127.0.0.1:1080`.
   Прокси применяется и к загрузчику, и ко встроенному браузеру (`session.setProxy`).
2. **Регион подбирается под прокси** на вкладке «Гео-обход». Регион, оператор,
   часовой пояс и язык берутся из одного профиля и не противоречат друг другу.
3. **Cookies из браузера** (`chrome`, `firefox`, `edge`, `brave`, `opera`, `safari`) или
   свой файл cookies в формате Netscape — если TikTok требует вход, подтверждение
   возраста или аккаунт для региона.
4. **Эмулируемое устройство закрепляется** при первом запуске и переиспользуется:
   постоянный `device_id`/`iid` нужен, потому что TikTok реагирует на смену устройства.

### Исправленная ошибка в движке

yt-dlp отправляет регион жёстко зашитым в `US` (`current_region`, `sys_region`,
`residence`, `carrier_region`, `op_region`, `timezone_name=America/New_York`), а через
`--extractor-args` это не переопределяется — там доступны только `api_hostname`,
`app_info`, `device_id`. Поэтому файлы по-прежнему качает yt-dlp, а метаданные и списки
по умолчанию получает собственный клиент (`Движок метаданных: Авто`).

Отдельно устранена ошибка, из-за которой приложение само выключало рабочий путь:
при пустом `apiHostname` в аргументы уходило `tiktok:api_hostname=www.tiktok.com`,
то есть yt-dlp переключался с мобильного API (работает без подписи) на веб-путь
(требует подписи, чаще упирается в геоблок). Теперь при пустом значении параметр не
передаётся вовсе и используется мобильный хост по умолчанию.

### Проверка

Кнопка **«Проверить»** на вкладке «Гео-обход» прогоняет реальный запрос и показывает,
какой движок ответил и какое разрешение вернулось. **Справка → Диагностика окружения**
печатает заявленный регион, оператора, таймзону, `device_id` и реальную страну IP.
Чекбокс «Показать параметры запроса» выводит полный набор уходящих параметров —
удобно для отладки конкретной комбинации.

## Запуск из исходников

```bash
npm install          # тянет Electron и бинарники в vendor/bin
npm start            # запуск
npm run dev          # запуск с devtools
npm run dist:win     # NSIS + portable .exe
npm run dist:linux   # AppImage + .deb
```

Требуется Node.js 18+.

`npm install` дополнительно скачивает `yt-dlp` и `ffmpeg` в `vendor/bin` — эта папка
в репозиторий не попадает, в репозитории лежит только `vendor/x-gnarly`. Собирать
дистрибутив нужно после `npm install`, иначе в сборку не попадут бинарники.

### Диагностика

Меню **Справка → Диагностика окружения** показывает пути к yt-dlp/ffmpeg, активный
прокси, регион и cookies. **Справка → Обновить yt-dlp** обновляет движок на месте.

## Автономный selftest

```bash
npx electron . --selftest
```

Поднимает локальный HTTP-сервер с 3 МБ данных и прогоняет весь путь загрузки:
сборка аргументов, парсинг `PROG`-прогресса, шаблон вывода, создание папки, чтение
размера файла. Это не зависит от доступности TikTok с машины сборки.

```json
{"done":true,"size":3145728,"sizeOnDisk":3145728,"progressSeen":true}
```

Дополнительно проверяется слой обхода региона: что в профиле `BY` стоят именно
`life:)` / `25704` / `Europe/Minsk` / UTC+3, что все шесть полей региона
(`region`, `current_region`, `sys_region`, `residence`, `carrier_region`, `op_region`)
уходят в запрос как `BY`, что идентификатор устройства стабилен между вызовами, что
рассогласование IP и региона обнаруживается, и что yt-dlp не переключается на
подписанный веб-хост по умолчанию.

Также проверяются классификатор ссылок (9 кейсов: видео, короткая ссылка, лента,
профиль, хештег, звук, чужой сайт, пустая строка), отказ `probe` для ссылки на ленту с
кодом `unsupported-url`, сбор видео с локальной страницы, имитирующей TikTok (три
уникальных видео из пяти якорей — с дублем и не-видео ссылкой, сохранение накопленного
списка при повторном сборе и рабочий скролл контейнера), а также определение текущего
видео: `<video>` с **blob-** источником (как в настоящей ленте) корректно превращается в
каноническую ссылку `https://www.tiktok.com/@now.user/video/7000000000000000009` — и по
текущему играющему ролику, и по координатам правого клика.

Отдельно проверяется обработка ссылок, открываемых в новой вкладке: фикстура с
настоящими синтетическими кликами (не через `executeJavaScript` — у него нет user
activation, и блокировщик всплывающих окон его отбивает) внутри `<webview allowpopups>`.
Проверка требует, чтобы гостевой странице доставили оба запроса — и она нужна, чтобы
никто не «починил» предупреждение Electron удалением `allowpopups` и не сломал при
этом внешние ссылки.

Селектор формата проверяется отдельно: ни в одном его звене не должно быть фильтра по
`format_note` (он отбрасывает все чистые форматы), каждое звено обязано содержать
`format_id!=download`, в конце не должно оставаться голого `/best`, а ограничение
высоты не должно стоять в последнем звене — иначе любой лимит молча ломает загрузку.

## Где берутся yt-dlp и ffmpeg

`scripts/postinstall.js` кладёт их в `vendor/bin`. Эта папка не коммитится — она
platform-specific и пересоздаётся командой выше, — поэтому в клонированном репозитории
её нет, а в собранном дистрибутиве она появляется через `extraResources`. Если загрузка
бинарника не удалась (например, ffmpeg для Linux собирается из tar-архива и требует
системного пакета), приложение работает и без них: фолбэк на `PATH`, а настройка
«Папка с yt-dlp / ffmpeg» позволяет указать путь вручную.

`vendor/x-gnarly` — единственная часть `vendor/`, которая **коммитится**: это 11 КБ
исходников на JS со своей лицензией MIT, и без них слой подписей (`src/main/signer.js`)
не запустится.

## Структура

```
src/main/main.js       окно, меню, IPC, прокси для сессии, selftest
src/main/ttapi.js      клиент мобильного API TikTok с подменой региона
src/main/regions.js    профили регионов: операторы (MCC/MNC), таймзоны, языки, app_info
src/main/geo.js        определение страны по IP и проверка согласованности с регионом
src/main/engine.js     выбор движка: мобильный API с откатом на yt-dlp
src/main/feed.js       сбор видео из отрисованной страницы webview (лента рекомендаций)
src/main/signer.js     слой подписей: X-Gnarly (встроенный) + опциональный Python sidecar
src/main/ytdlp.js      аргументы, загрузка, очередь, прогресс, отмена, маппинг ошибок,
                       классификация ссылок (видео / лента / профиль / хештег / звук)
src/main/binaries.js   поиск yt-dlp/ffmpeg: override → vendor/bin → PATH
src/main/settings.js   настройки в userData/settings.json, SCHEMA_VERSION + raw() для миграций
src/preload/preload.js contextBridge, без nodeIntegration
src/preload/webview-preload.js preload гостя: перехват правого клика, гашение меню страницы
src/renderer/          UI: index.html, styles.css, renderer.js
scripts/postinstall.js загрузка бинарников
vendor/x-gnarly/       вендоренный encode.js/decode.js (MIT, justscrapeme) — в репозитории
vendor/bin/            yt-dlp и ffmpeg — не в репозитории, скачивает postinstall
```

`vendor/` попадает в сборку через `extraResources`, поэтому и `binaries.js`, и `signer.js`
ищут файлы по списку корней (dev: `<repo>/vendor/...`, packaged:
`<resources>/vendor/...`) через `setResourcesRoot()`, а не по одному жёсткому пути от
`__dirname` — иначе в packaged-сборке путь указывал бы внутрь `app.asar`, где
`vendor/` нет.
